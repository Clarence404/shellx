# Monitor threshold alerts

Status: approved 2026-10-12, implemented on `feat/monitor-alerts`. Targets
v0.36.0 (the date and version in this file's name match the mockup's, so the two
sort and compare together).
Mockup: [`docs/mockups/2026-10-12-v0.36-monitor-threshold-alerts.html`](../../mockups/2026-10-12-v0.36-monitor-threshold-alerts.html) — open in
a browser; it is a clickable prototype with fake data and is the canonical
visual reference (settings page, Alerts tab, toast, sidebar badge).

The monitor already reads CPU, memory, disk, load and failed units off every
connected host, but only shows them. You find out a disk filled up by going and
looking. This turns those readings into **alerts**: rules with thresholds, and
somewhere for a crossed threshold to surface.

## Decisions

**Sampling is decoupled from the monitor panel.** Before this, the poll loop
started when a `MonitorPanel` mounted and stopped when it unmounted, so alerts
would only have fired while you were already watching the thing they were
telling you about. Now a single app-level bridge (`state/monitorBridge.ts`)
owns every start/stop: an open panel claims its chosen rate, and any other
connected SSH session is sampled at 10 seconds while alerts are on. A session
closing, or alerts being switched off, stops its loop. `desiredIntervals()` is
the whole policy as one pure function, so it is tested without a backend.

**Rules are evaluated in TypeScript, not Rust.** The backend keeps emitting the
same `monitor:snapshot` events it always did; nothing about the Rust monitor
changed. The rule engine (`state/alertRules.ts`) folds each snapshot into the
alerts carried over from the previous one. This kept the change almost entirely
in the frontend, and makes the hard part — sustain counts, hysteresis,
cooldowns — a pure function with `now` passed in, so cooldowns are tested
without waiting. The cost is that alerts stop if the webview is gone, which on
a desktop app means the app is closed anyway.

**One global set of thresholds, in Settings → Alerts.** Per-host thresholds
were considered and deferred: they need a hosts column, a form field, and a
second place to look when an alert surprises you. A DB server that idles at 85%
memory is the case that will eventually force per-host overrides; until someone
hits it, one set of numbers is less to explain. The panel lives in Settings
rather than inside the monitor so it sits with the rest of the configuration;
the Alerts tab links across to it.

**Off by default.** `AlertSettings::default()` has `enabled: false`, and a
`settings.json` written before v0.36 deserializes to exactly that. Upgrading
never starts notifying on its own.

**Three guards against noise**, all tunable:

- *Sustain* — a rule must breach N consecutive samples (default 3) before it
  fires, so a one-tick spike is not a notification. A failed unit is exempt: it
  is already a fact when first seen.
- *Cooldown* — a rule that stays breached re-fires at most every N minutes
  (default 10). An hour of high CPU is one alert, not six hundred.
- *Hysteresis* — an alert clears only once the reading falls 5 points below its
  threshold. Without it, a metric sitting on the line alerts and recovers on
  alternating samples.

**Alerts are in memory only.** No table, no file; closing shellx forgets them.
They are a "look at this now" signal, not a log — the host itself has the
history. A recovered alert stays visible for 10 minutes, then ages out, and
each connection is capped at 50 so a host with dozens of failed mounts cannot
grow the list without bound.

**Four surfaces, one source.** A fired alert raises a toast (bottom-right, 8s),
an OS notification (via `tauri-plugin-notification`, opt-out), a badge on the
sidebar host row, and an entry in the monitor's Alerts tab. The tab had
previously held only `systemctl --failed`; threshold alerts now sit above that
list. A failed unit is listed once — in the units section, which has its
result, exit status and copyable command — rather than twice.

## Rules

| Rule | Reads | Default |
| --- | --- | --- |
| CPU | `cpu.totalPct` | on, 85% |
| Memory | `used / total`, excluding cache — the same number the KPI tile shows | on, 90% |
| Disk | `usePct`, one alert per mount | on, 90% |
| Swap | `swapUsed / swapTotal`, skipped on hosts without swap | off, 50% |
| Load per core | 1-minute load ÷ core count | off, 2x |
| Failed services | a unit entering `systemctl --failed` | on |

## Shape

- `types/alerts.ts` — `AlertSettings`, `Alert`, defaults, ranges. Mirrored by
  `AlertSettings` in `src-tauri/src/settings/mod.rs`, whose `sanitized()`
  clamps to the same ranges.
- `state/alertRules.ts` — `readings()` and `evaluate()`; pure.
- `state/alerts.ts` — the store: per-connection alert lists, ageing, selectors
  for the tab and the sidebar badge.
- `state/monitorBridge.ts` — the one global snapshot subscriber, start/stop
  policy, and announcing fired alerts.
- `state/alertText.ts` — one place that turns an `Alert` into words, so the
  toast, the tab and the OS notification cannot drift.
- `components/settings/AlertsPanel.tsx`, `components/monitor/AlertsTab.tsx`,
  `components/AlertToasts.tsx`, badge in `HostRow`.

## Not doing

- **Per-host thresholds** — see above; the first real conflict should drive it.
- **Alert history / persistence** — no table. If this is wanted later it is a
  new store, not a change to these rules.
- **Custom rules** (arbitrary commands, process-level watches) — a different
  feature with its own editing UI.
- **Alerting on disconnected hosts** — no session means no readings. Reaching
  a host that is down needs a reconnect policy, which is its own decision.
