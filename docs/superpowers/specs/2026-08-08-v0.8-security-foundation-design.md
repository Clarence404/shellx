# shellx v0.8 — Security Foundation (host-key TOFU + public-key auth)

Status: **approved design, pending implementation plan**
Mockups: [`mockups/v0.8/`](mockups/v0.8/) — open in a browser; `v08-full-ui-styleA.html` is the canonical UI reference.
Deferred sibling: port forwarding (`-L`) is v0.9 — its approved mockups are archived at [`mockups/v0.9-tunnels/`](mockups/v0.9-tunnels/).

## 1. Goal

Remove the two blockers that make shellx unsafe / incomplete for public release:

1. **No server identity verification.** Every server is trusted unconditionally — a MITM on any shared network silently captures credentials. Fix: trust-on-first-use (TOFU) host-key verification backed by `~/.ssh/known_hosts`.
2. **Password-only auth.** Users with `~/.ssh/id_ed25519` (i.e. most target users) can't connect the way they already work. Fix: public-key authentication with passphrase stored in the OS keychain.

Success criterion: the README's "do not use over untrusted networks" warning is deleted, and the user's daily `ssh -i ~/.ssh/id_ed25519 chen.han@bastion` is fully replaced by one click (the `-L` half of their command arrives in v0.9).

## 2. Decisions locked during design review

| # | Decision | Choice | Rationale |
|---|----------|--------|-----------|
| D1 | known_hosts location | **Shared `~/.ssh/known_hosts`** | User already has 15 entries accumulated from CLI ssh; cross-tool trust is the SSH ecosystem convention. |
| D2 | known_hosts write discipline | **Append-only. Never rewrite, never delete, never reorder.** | Worst-case bug adds a redundant line instead of destroying existing trust data. Matches OpenSSH's own behavior. |
| D3 | First-connection UX | **Confirmation dialog** showing host, key type, SHA256 fingerprint ("方案 B") | Public-release security tools should make first trust an explicit user decision. Frequency is once per server, ever. |
| D4 | Fingerprint mismatch UX | **Blocking red dialog, default action = cancel.** Old + new fingerprints shown side by side. Continue is a de-emphasized ghost button. | Make leaving easier than proceeding. |
| D5 | Auth methods | **publickey (Ed25519 / RSA / ECDSA) + password.** keyboard-interactive: silent fallback only (auto-answer password-like prompts with the stored password); no interactive prompt UI. | User's bastions don't use OTP. Full kbd-interactive UI deferred until someone needs it. |
| D6 | Passphrase storage | **OS keychain via the same `keyring` path used for passwords today** (Windows Credential Manager / macOS Keychain / Linux Secret Service). UI copy says "系统密钥链 / OS keychain" — platform-neutral. | Cross-platform is a stated design principle. No custom encrypted stores. |
| D7 | Key discovery | Scan `~/.ssh/` once when the host form opens. Detect by **reading each file's first line** (private-key PEM/OpenSSH headers), NOT by `.pub` pairing — user's own `platform-svc` key has no `.pub` and must be found. Exclude `known_hosts*`, `config`, `authorized_keys`, `*.pub`. | Real-world keys frequently lack `.pub` siblings. |
| D8 | Key metadata | Type + comment read from the **embedded public part** of the private key (what `ssh-keygen -l` does). No decryption, no passphrase needed for listing. | Fast, safe, no prompts during discovery. |
| D9 | Foreign formats | **PPK (PuTTY)**: detect, list with a "needs conversion" hint + one-line `puttygen` instruction. **SSH2/Tectia**: detect, mark unsupported. **-SK (FIDO2)** & **certificates**: out of scope, detected → tooltip. | PPK users are a large share of the Windows audience; a hint retains them, silence loses them. |
| D10 | Weak keys | RSA-1024 / DSA are listed but visually de-emphasized with a ⚠ badge. Selectable (user may have no choice) but never auto-preselected. | Honest middle ground. |
| D11 | Default auth mode | Form opens in **key mode with best key preselected** (Ed25519 > RSA-4096 > others) when ≥1 key discovered; otherwise password mode. | Zero-click for key users, no confusion for password users. |
| D12 | Key picker form factor | Adaptive: 0 keys → browse only; 1–4 keys → inline chips; ≥5 keys → searchable dropdown (↑↓/Enter navigation, ED25519 sorted first). | Covers casual through power users without cluttering the common case. |
| D13 | ssh-agent / Pageant | **Deferred to v0.9+.** Keychain-stored passphrases already deliver the daily UX (zero prompts). | Agent integration is an independent feature (protocol client + forwarding); bundling would double v0.8 scope. |
| D14 | Trusted-servers management | Read-only list in Settings (host / type / fingerprint / copy button). **No delete button** — deletion is rare + dangerous; users edit the file manually. | Conservative start; revisit if requested. |
| D15 | UI style | **Style A** — existing warm-minimal dark tokens. Borrowed details: chip/card key picker (from style B), Enter/Esc keyboard hints on dialogs (from style C). | Zero redesign cost, consistent app. |

## 3. Architecture

### 3.1 Rust side

New module `src-tauri/src/hostkeys/`:

```
hostkeys/
├── mod.rs          — public API: check(host, port, key) -> KnownHostsVerdict
│                     append(host, port, key) -> Result<()>
│                     list() -> Vec<TrustedHost>       (Settings read-only view)
└── file.rs         — ~/.ssh/known_hosts parse (via russh-keys / ssh-key crate),
                      append-only writer (create parent dir + file if missing,
                      0600 on unix), hashed-hostname (`|1|…`) entries MATCHED
                      but never produced
```

`KnownHostsVerdict` enum: `Match` | `Unknown` | `Mismatch { stored: Fingerprint }`.

Integration point: russh's `client::Handler::check_server_key`. Today it returns `Ok(true)` unconditionally. New flow:

1. Compute verdict via `hostkeys::check`.
2. `Match` → `Ok(true)`, proceed.
3. `Unknown` / `Mismatch` → emit a `hostkey:challenge` Tauri event carrying `{ connection_attempt_id, host, port, key_type, fingerprint_sha256, verdict, stored_fingerprint? }`, then **await a oneshot channel** the frontend resolves via a new `hostkey_respond` IPC command (`accept: bool`). Accept on Unknown appends to known_hosts before returning `Ok(true)`. Accept on Mismatch appends the new key (OpenSSH matches any line). Reject → `Ok(false)` → connection fails with a typed error the frontend maps to "user declined host key".
4. Timeout (120 s) → treat as reject, so an abandoned dialog can't hold a task forever.

New module `src-tauri/src/keys/`:

```
keys/
├── mod.rs          — discover() -> Vec<DiscoveredKey>   (form-open scan)
│                     load(path, passphrase) -> PrivateKey (russh-keys decode_secret_key)
└── detect.rs       — first-line header classification:
                      OpenSSH / PKCS#1 RSA / EC / DSA / PKCS#8 → Supported(format)
                      PuTTY-User-Key-File → Ppk
                      BEGIN SSH2 → Ssh2
                      else → NotAKey
                      + public-part metadata extraction (type, bits, comment)
```

`DiscoveredKey { path, file_name, kind: Supported{algo,bits}|Ppk|Ssh2, comment, encrypted: bool }`.

Auth flow changes in `protocol/ssh.rs`:

- Host record gains `auth_method` (`"password"` \| `"publickey"`) and `key_path`.
- publickey: load key (passphrase from keychain → if missing/declined, emit `auth:passphrase-needed` event and await frontend response, same oneshot pattern as host keys) → `authenticate_publickey`.
- On publickey rejection: typed error → frontend shows the three-exit failure dialog (switch to password / pick another key / retry).
- password auth unchanged; silent kbd-interactive fallback added when the server rejects the "password" method but offers keyboard-interactive: answer prompts matching `/pass(word|phrase)/i` with the stored password, fail cleanly on any other prompt text.

Keychain: passphrase entries live beside password entries, service key `shellx-passphrase:<host_id>` (existing password entries stay `shellx:<host_id>`). Wrong passphrases are never written to the keychain (only persisted after a successful key decode).

### 3.2 Data model

`hosts` table (SQLite migration):

```sql
ALTER TABLE hosts ADD COLUMN auth_method TEXT NOT NULL DEFAULT 'password';
ALTER TABLE hosts ADD COLUMN key_path TEXT;               -- absolute path, forward slashes
```

No migration needed for existing rows (default `'password'` preserves behavior).

### 3.3 Frontend

New/changed pieces (canonical visuals: `mockups/v0.8/v08-full-ui-styleA.html`):

| Piece | Nature | Notes |
|---|---|---|
| `HostForm` auth section | modify | segmented publickey/password, adaptive key picker (chips ↔ searchable dropdown per D12), passphrase field. Edit mode: blank-keeps, "forget stored passphrase" checkbox. |
| `HostKeyDialog` | new | Handles both TOFU-confirm (purple) and mismatch-warning (red) from the `hostkey:challenge` event. Enter/Esc keyboard shortcuts; mismatch variant defaults focus to Cancel. |
| `PassphraseDialog` | new | Prompt + "remember in keychain" checkbox; inline retry state (red border + attempt counter, max 3). |
| `AuthFailedDialog` | new (extends ErrorDialog pattern) | Three exits: switch to password / choose another key / retry. |
| Settings → "Trusted servers" | new | Read-only known_hosts list with copy-fingerprint buttons (D14). |
| `ipc/hostkeys.ts`, `ipc/keys.ts` | new | Typed wrappers: `hostkeyRespond`, `keysDiscover`, plus `listen("hostkey:challenge")`, `listen("auth:passphrase-needed")`. |
| State | modify | A small `usePendingChallenges` store keyed by `connection_attempt_id` so dialogs survive re-renders and two simultaneous connects can't cross wires. |

### 3.4 Event/IPC contract summary

```
Rust → JS events
  hostkey:challenge         { attemptId, host, port, keyType, fingerprint, verdict, storedFingerprint? }
  auth:passphrase-needed    { attemptId, keyPath, attempt, maxAttempts }

JS → Rust commands
  hostkey_respond           { attemptId, accept }
  auth_passphrase_respond   { attemptId, passphrase | null, remember }
  keys_discover             -> DiscoveredKey[]
  hostkeys_list             -> TrustedHost[]         (Settings view)
```

## 4. Error handling

| Failure | Behavior |
|---|---|
| known_hosts unreadable (permissions) | Treat every host as Unknown; dialog shows a non-blocking note "无法读取 known_hosts，本次信任不会被保存". Never crash the connect path. |
| known_hosts append fails | Connection proceeds (user explicitly accepted); ErrorDialog explains trust wasn't persisted and next connect will re-ask. |
| Key file unreadable / malformed | AuthFailedDialog with the parse error, exits per D-flow. |
| Wrong passphrase | Inline retry in PassphraseDialog (≤3), then AuthFailedDialog. Never cached. |
| Keychain unavailable (headless Linux) | "remember" checkbox hidden; passphrase prompted per session (matches existing password behavior). |
| User closes challenge dialog / 120 s timeout | Connect attempt fails with "declined by user"; no partial state. |

## 5. Testing

- **Rust unit**: known_hosts parse (plain, hashed `|1|`, multi-key host, comment lines), append-only writer (file created 0600, concurrent-append safety via O_APPEND), key detection matrix (each header type + PPK + SSH2 + junk), metadata extraction on an unencrypted and an encrypted fixture key.
- **Rust integration** (existing in-process russh fixture, extended): key-auth happy path; TOFU flow with a scripted accept; mismatch detection (fixture server swaps keys between runs); kbd-interactive fallback.
- **Frontend (vitest)**: HostKeyDialog both variants incl. keyboard shortcuts + default focus; PassphraseDialog retry counter; HostForm adaptive picker (0 / 3 / 6 discovered keys) and default-mode selection (D11); challenge-store isolation across two attemptIds.
- **Manual gate (ship checklist)**: connect to a fresh VM (TOFU dialog) → reconnect (silent) → alter server key (red dialog) → user's real `platform-svc` no-`.pub` key appears in discovery.

## 6. Out of scope (v0.8)

ssh-agent / Pageant (D13) · port forwarding `-L` (v0.9, mockups archived) · full keyboard-interactive UI / OTP (D5) · FIDO2 `-SK` keys & SSH certificates (D9) · known_hosts entry deletion UI (D14) · host-key algorithms negotiation UI.

## 7. Release note seed

> shellx now verifies server identity (TOFU against `~/.ssh/known_hosts`, shared with command-line ssh) and supports public-key login (Ed25519 / RSA / ECDSA) with passphrases stored in the OS keychain. First connection to a new server asks you to confirm its fingerprint once; a changed fingerprint is blocked with a warning. The "untrusted networks" caveat is gone from the README.
